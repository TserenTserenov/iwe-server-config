# /wp-prepare — конвейер подготовки РП к Менеджеру РП

> **Основание:** план РП-626 «Менеджер РП» (принят пилотом 25.11), разделы 2.1 и 2.3; правило «Описание готово» в соглашении о папках РП (`<репозиторий управления>/docs/INBOX-CONVENTION.md`); код изменения Ц38-22. Статус `experimental`: первый прогон — РП-568 (25.11, срез дымового прогона). Менеджер РП обкатывается в IWE автора, затем поставляется пользователям шаблона — навык не использует личных путей автора.

## When to use

Пилот говорит «подготовь РП-N к Менеджеру» или «доведи описание РП-N до готовности»; Менеджер РП на приёме (этап М0) вернул РП с перечнем пробелов; перед первым прогоном Менеджера на любом РП. Не для РП, который Менеджеру не передаётся: там раздел «описание готово» не нужен.

## Обещание

**Вход:** номер РП-N и замысел пилота (цель, результат, приёмка, права, бюджет) — словами пилота или из карточки.
**Выход:** у РП-N есть файл договоров фаз (`inbox/WP-N/contracts.yaml`), карточка помечена `manager: candidate`, механическая проверка пишет «готово», два независимых проверяющих согласны (расхождение не больше одного места), вопросы о цели решены пилотом, и пилот сказал «да» — допуск записан в карточке.
**Инвариант:** решения о цели, составе фаз и правах «только пилот» принимает пилот; агент готовит варианты. Описание не меняется во время прогона Менеджера: правка после допуска — новая версия (`version`) и новый допуск.

## Algorithm

Сессия открывается на РП-N (не на РП-503): договоры и карточка — документы РП-N.

### 1. Замысел пилота
Собрать из карточки и слов пилота: цель и результат, приёмку целого (критерий и проверяющий), права (что агент решает сам, что выносит на подтверждение, что только пилот), бюджет и предел параллельности. Чего нет — один вопрос пилоту на пункт, не больше двух вопросов за подход. Права задаются правилами P1–P19 таблицы прав Менеджера (план РП-626 Ф2; уровни по умолчанию — в его программе журнала `scripts/wp-run-journal.py`). Спрашивать только о повышении (например, `P8: pilot-only` — развилки по цели решает пилот); P14–P18 (работа другого РП, постановка, бюджет, пак и стратегия, внешнее и необратимое) уже «только пилот». Известные заранее развилки «только пилот» записать в `decisions`.

### 2. Разложение на фазы-договоры (Декомпозитор, навык `/decompose`)
Открытые фазы РП-N — в договоры по таблице соглашения: класс `И` / `Ф` / `Ц` (смешанную фазу делить на части `ФN.xф`, `ФN.xц`), вход, выход, вид результата, функциональная часть, метод, проверка, оценка и потолок, `after`. Дубли фаз — слить до разметки. Неизвестное — в реестр допущений с Ф-фазой или принятым риском. Если прогон Менеджера берёт не весь РП — `run_scope`. Записать `inbox/WP-N/contracts.yaml`, в карточке — `manager: candidate`, `contracts: contracts.yaml`.

### 3. Приоритеты (Стратег, с согласия пилота)
Порядок фаз внутри области прогона — из `after`; что идёт первым при равных — предложить пилоту одной строкой с основанием. Без «да» пилота порядок не фиксировать.

### 4. Механическая проверка
```bash
python3 "${IWE_WORKSPACE:-$HOME/IWE}/${IWE_GOVERNANCE_REPO:-DS-strategy}/scripts/check-wp-readiness.py" \
  --repo "${IWE_WORKSPACE:-$HOME/IWE}/${IWE_GOVERNANCE_REPO:-DS-strategy}" --wp N
```
Последняя строка «пробелов K» → вернуться к шагу 2. «готово» → шаг 5.

### 5. Два независимых проверяющих
Два агента, не писавшие описание, по возможности разных вендоров (в IWE с напарниками пир-сессии — два разных вендора, например `kimi` и `codex`; без напарников — два отдельных запуска разных моделей), получают ТОЛЬКО карточку РП-N и файл договоров текстом и не видят ответов друг друга (запускать параллельно). Задание — файл `reviewer-prompt.md` рядом с этим навыком: подставить РП, область прогона, имя проверяющего и версию договоров, приложить карточку и договоры. По каждой фазе области прогона каждый отвечает в формате отзыва: `first_step`, `how_to_check`, `questions` (у вопроса место `ФN.поле` или `wp.поле`, разметка `goal` / `fact` / `risk`, текст). Задание отсекает три вида шума, найденные на первом прогоне (РП-568, 25.11): «готова ли предыдущая фаза», «какой вариант выбрать» у фазы класса Ц, «существует ли документ из входа». Это **проход 1**.
**Проход 2 (перекрёстный, правило А′ — решение пилота 25.11).** Каждому проверяющему дать пронумерованные вопросы и первые шаги другого:
```bash
python3 "<репозиторий управления>/scripts/compare-readiness-reviews.py" questions отзыв-другого.yaml
```
и задание `cross-review-prompt.md` рядом с этим навыком. По каждому чужому вопросу — вердикт `gap` (пробел), `first_step` (исполнитель снимет первым шагом) или `not_gap` (ответ уже есть, с местом ответа `ФN.поле` или `wp.поле`); по каждой фазе — `same_action: yes|no` (то же ли первое действие). Снова параллельно.

Счёт:
```bash
python3 "<репозиторий управления>/scripts/compare-readiness-reviews.py" score отзыв-1.yaml отзыв-2.yaml вердикты-1.yaml вердикты-2.yaml --phases <область прогона через запятую>
```
Расхождение — вопросы с `not_gap` и фазы с `same_action: no`; `not_gap` с местом `wp.decisions` (вопрос уже записан развилкой пилота) — не расхождение, а вопрос пилоту.
- «неоднозначно» (расхождений больше одного), «отзыв неполон» или подтверждённые обоими пробелы о факте или риске → описание на доработку, шаг 2 (о факте — Ф-фаза или правка, риск — в реестр допущений);
- «однозначно» → подтверждённые вопросы о цели — развилками пилоту (`decisions`, шаг 6); уточнения `first_step` — в список для исполнителя, не блокируют;
- после трёх кругов без «однозначно» — спорные места пилоту списком, четвёртый круг не запускать.

Отзывы, вердикты и итог счёта сохранить в журнале сессии.

### 6. Решения пилота и допуск
Пилоту — по одному вопросу о цели, с вариантами и рекомендацией (не больше двух за подход). Решения записать в договоры (новая `version`, если допуск уже был). Затем одна строка пилоту: «РП-N готов к Менеджеру: область прогона …, бюджет …, вопросы закрыты. Допускаем?». Только на «да» — запись в шапке карточки:
```yaml
manager_admission: {date: <YYYY-MM-DD>, version: <version договоров>, pilot_word: "<слово пилота дословно>", contracts_sha256: <отпечаток файла договоров>}
```
Отпечаток: `shasum -a 256 inbox/WP-N/contracts.yaml` (или `sha256sum`). После записи — повторить шаг 4: проверка сверяет отпечаток. После этого Менеджер (`/wp-manager`) принимает РП на этапе М0.

## Режим отказа

| Сценарий | Поведение |
|---|---|
| Нет программы проверки готовности в репозитории управления | сказать пилоту, что установка не обновлена (поставка — РП-529); механический шаг не подменять чтением глазами |
| Напарник-проверяющий недоступен | второго проверяющего — другим запуском другой модели; одного проверяющего мало, допуск не давать |
| Проверяющие видели ответы друг друга | отзывы недействительны, повторить шаг 5 |
| Пилот не ответил на вопрос о цели | фаза остаётся с вопросом, допуск не даётся; остальные шаги не ждут |
| Описание правят после допуска | проверка готовности сообщает «договоры изменены после допуска» (отпечаток не совпал); новая `version`, новый допуск |
