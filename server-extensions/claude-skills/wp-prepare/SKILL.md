# /wp-prepare — конвейер подготовки РП к Менеджеру РП

> **Основание:** план РП-626 «Менеджер РП» (принят пилотом 25.11), разделы 2.1 и 2.3; правило «Описание готово» в соглашении о папках РП (`<репозиторий управления>/docs/INBOX-CONVENTION.md`); код изменения Ц38-22. Статус `experimental`: первый прогон — РП-568 (25.11, срез дымового прогона). Менеджер РП обкатывается в IWE автора, затем поставляется пользователям шаблона — навык не использует личных путей автора.

## When to use

Пилот говорит «подготовь РП-N к Менеджеру» или «доведи описание РП-N до готовности»; Менеджер РП на приёме (этап М0) вернул РП с перечнем пробелов; перед первым прогоном Менеджера на любом РП. Не для РП, который Менеджеру не передаётся: там раздел «описание готово» не нужен.

## Обещание

**Вход:** номер РП-N и замысел пилота (цель, результат, приёмка, права, бюджет) — словами пилота или из карточки.
**Выход:** у РП-N есть файл договоров фаз (`inbox/WP-N/contracts.yaml`), карточка помечена `manager: candidate`, механическая проверка пишет «готово», два независимых проверяющих согласны (расхождение не больше одного места), вопросы о цели решены пилотом, и пилот сказал «да» — допуск записан в карточке.
**Инвариант:** решения о цели, составе фаз и правах «только пилот» принимает пилот; агент готовит варианты. Описание не меняется во время прогона Менеджера: правка после допуска — новая версия (`version`) и новый допуск.

## Algorithm

Сессия открывается на РП-N (не на РП-503): договоры и карточка — документы РП-N.

### 1. Замысел пилота
Собрать из карточки и слов пилота: цель и результат, приёмку целого (критерий и проверяющий), права (что агент решает сам, что выносит на подтверждение, что только пилот), бюджет и предел параллельности. Чего нет — один вопрос пилоту на пункт, не больше двух вопросов за подход. Права «только пилот» по умолчанию (пак, стратегия, бюджеты, статусы и закрытие РП) не спрашивать — они уже действуют.

### 2. Разложение на фазы-договоры (Декомпозитор, навык `/decompose`)
Открытые фазы РП-N — в договоры по таблице соглашения: класс `И` / `Ф` / `Ц` (смешанную фазу делить на части `ФN.xф`, `ФN.xц`), вход, выход, вид результата, функциональная часть, метод, проверка, оценка и потолок, `after`. Дубли фаз — слить до разметки. Неизвестное — в реестр допущений с Ф-фазой или принятым риском. Если прогон Менеджера берёт не весь РП — `run_scope`. Записать `inbox/WP-N/contracts.yaml`, в карточке — `manager: candidate`, `contracts: contracts.yaml`.

### 3. Приоритеты (Стратег, с согласия пилота)
Порядок фаз внутри области прогона — из `after`; что идёт первым при равных — предложить пилоту одной строкой с основанием. Без «да» пилота порядок не фиксировать.

### 4. Механическая проверка
```bash
python3 "${IWE_WORKSPACE:-$HOME/IWE}/${IWE_GOVERNANCE_REPO:-DS-strategy}/scripts/check-wp-readiness.py" \
  --repo "${IWE_WORKSPACE:-$HOME/IWE}/${IWE_GOVERNANCE_REPO:-DS-strategy}" --wp N
```
Последняя строка «пробелов K» → вернуться к шагу 2. «готово» → шаг 5.

### 5. Два независимых проверяющих
Два агента, не писавшие описание, по возможности разных вендоров (напарники пир-сессии: `kimi`, `codex`), получают ТОЛЬКО карточку РП-N и файл договоров текстом и не видят ответов друг друга (запускать параллельно). Задание — файл `reviewer-prompt.md` рядом с этим навыком: подставить РП, область прогона, имя проверяющего и версию договоров, приложить карточку и договоры. По каждой фазе области прогона каждый отвечает в формате отзыва: `first_step`, `how_to_check`, `questions` (у вопроса место `ФN.поле` или `wp.поле`, разметка `goal` / `fact` / `risk`, текст). Задание отсекает три вида шума, найденные на первом прогоне (РП-568, 25.11): «готова ли предыдущая фаза», «какой вариант выбрать» у фазы класса Ц, «существует ли документ из входа». Сверка:
```bash
python3 "<репозиторий управления>/scripts/compare-readiness-reviews.py" отзыв-1.yaml отзыв-2.yaml --phases <область прогона через запятую>
```
- «неоднозначно» (мест, названных только одним проверяющим, больше одного) или «отзыв неполон» → описание на доработку, шаг 2;
- «однозначно» → вопросы о факте — добавить Ф-фазы (шаг 2), принятые риски — в реестр допущений, вопросы о цели — карточками решений пилоту (шаг 6).

Отзывы и итог сверки сохранить в журнале сессии.

### 6. Решения пилота и допуск
Пилоту — по одному вопросу о цели, с вариантами и рекомендацией (не больше двух за подход). Решения записать в договоры (новая `version`, если допуск уже был). Затем одна строка пилоту: «РП-N готов к Менеджеру: область прогона …, бюджет …, вопросы закрыты. Допускаем?». Только на «да» — запись в шапке карточки:
```yaml
manager_admission: {date: <YYYY-MM-DD>, version: <version договоров>, pilot_word: "<слово пилота дословно>"}
```
После этого Менеджер (`/wp-manager`) принимает РП на этапе М0.

## Режим отказа

| Сценарий | Поведение |
|---|---|
| Нет программы проверки готовности в репозитории управления | сказать пилоту, что установка не обновлена (поставка — РП-529); механический шаг не подменять чтением глазами |
| Напарник-проверяющий недоступен | второго проверяющего — другим запуском другой модели; одного проверяющего мало, допуск не давать |
| Проверяющие видели ответы друг друга | отзывы недействительны, повторить шаг 5 |
| Пилот не ответил на вопрос о цели | фаза остаётся с вопросом, допуск не даётся; остальные шаги не ждут |
| Описание правят после допуска | новая `version`, `manager_admission` снимается до нового «да» |
