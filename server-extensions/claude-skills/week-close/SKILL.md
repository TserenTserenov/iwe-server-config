# Week Close (протокол закрытия недели)

> **Роль:** R1 Стратег. **Бюджет с пилотом: ~5-10 мин** (ретро + carry-over + R-вопросник + оценка недели) + **полное закрытие агент доводит один** (~20 мин, без пилота).
> **Принцип (DP.D.288, WP-484 30.07 — быстрое закрытие ≠ полное закрытие):** быстрое закрытие — короткая рефлексия и решения, которые нужны только пилоту; вся механика (сбор данных, метрики, платформенные проверки) — потом, агент один.
> **Принцип:** SKILL.md = L1 платформенный файл. Пользователь не редактирует напрямую — только через `extensions/`.
> **Стиль текста:** ретро недели и новый WeekPlan читает пилот → весь текст синтезировать в базе разговорного стиля (S0 база + S1 автор, источник DP.SC.050): русский, без машинных меток, главная мысль первой, код РП и путь не подлежащее.

## When to use

Протокол закрытия недели (Week Close). Ретро 7 дней + carry-over в новую неделю + платформенные шаги (бэкап, dirty repos).

## БЛОКИРУЮЩЕЕ: пошаговое исполнение

Week Close = протокол. Исполнять ТОЛЬКО пошагово через TodoWrite.
**Шаг 0 — ПЕРВОЕ действие:** создать список задач ТОЛЬКО для Части А (все шаги до «Ты свободен» включительно) — пилот не должен видеть механику Части Б раньше хендоффа (DP.D.288).
**Сразу после «Ты свободен»:** одним пакетом завести в списке задач все шаги Части Б — теперь можно, пилот уже свободен.
Каждый шаг алгоритма → отдельная задача (pending → in_progress → completed).

## ЧАСТЬ А. Быстрое закрытие (с пилотом, ~5-10 мин)

### 0. Предварительный свод недели [[narrative]]

> **WP-484, 31.07 — разрыв с day-close.** У дня уже есть этот шаг перед ретро-вопросом; у недели вопрос раньше шёл без предварительного свода — пилот получал вопрос «что сработало» без цифр, на которые можно опереться.

```bash
for repo in $(ls {{HOME_DIR}}/IWE/); do
  if [ -d {{HOME_DIR}}/IWE/$repo/.git ]; then
    commits=$(git -C {{HOME_DIR}}/IWE/$repo log --since="1 week ago" --oneline --no-merges 2>/dev/null \
      | grep -vE "^(docs|chore|ci|style|perf|test)(\\(|:| )" \
      | grep -vE "memory/|\.claude/rules/|template-sync|backup|reindex" \
      || true)
    count=$(echo "$commits" | grep -c . || true)
    [ "$count" -gt 0 ] && echo "$repo: $count"
  fi
done
```

Показать пилоту 3-5 строк: сколько коммитов за неделю по репозиториям + число закрытых/перенесённых РП (если уже известно на этот момент). Начать с подписи: **«Предварительный свод недели — снимок для рефлексии, не итоговые цифры»**. Числа, не список дел — то же самое «не хватало цифр», что и в дне. Окончательные цифры и проверки появятся в Части Б.

### 1. Единый блок вопросов недели (WP-484 Ф36, 01.08 — было 4 отдельных хода пилота, слито в один) [[gate]]

> Раньше ретро/carry-over/R-вопросник/оценка качества были четырьмя отдельными ожиданиями ответа подряд. Объединение не убирает ни один вопрос (все содержательно нужны, рефлексия обязательна — CONCEPT-night-cycle.md §22) — только сокращает число раз, когда пилот читает-и-отвечает.

Собрать carry-over список ДО вопроса (не заставлять пилота искать самому): РП с pending/in_progress статусом из WeekPlan текущей недели, коротко (номер+название).

Задать ОДНИМ сообщением, с явной структурой (пилот отвечает по пунктам или общей фразой, не обязан соблюдать формат):
- «Ретро недели: что сработало хорошо? Что не сработало, какой был самый большой блокер?»
- «Carry-over: вот список РП в работе — [список]. Переносим все как есть в новую неделю, или что-то меняется (закрыть/понизить приоритет/добавить)?»
- «R-вопросник (полный текст, критерии и антипаттерны → `memory/r-questionnaire.md`): (1) системный паттерн из отчёта о поведении/инцидентов за неделю — разовое или регулярное? (2) какой РП взял больше времени, чем планировалось, и почему одним словом? (3) если бы мог отменить одно действие этой недели — что?» («нечего ответить» — валидный ответ на любой из трёх; один и тот же вопрос без ответа 3 недели подряд → вопрос-кандидат на удаление из анкеты, решение пилота, не агента)
- «Оцени качество недели 1-5: 1=механически, 2=поверхностно, 3=норма, 4=хорошо, 5=прорывная» (пропуск — тоже валидный ответ)

Разнести ответы по получателям (объединение сообщения не объединяет хранилище):

**Ретро → ledger** (пустой ответ — писать «нет ответа», не пропускать):

### 2. Мост неделя→месяц: `week_summary` (WP-484 Нить 4) [[narrative]]

> **Не `[[gate]]`, сознательно (code review, 2026-07-30-11):** не входит ни в один из 6 гейтов, отслеживаемых `protocol-close.md § Week Close` — тег `[[gate]]` без соответствующего `mark-gate` не даёт трассировки и вводит в заблуждение. Шаг всё равно выполняется как часть нумерованного алгоритма (narrative = переставим, не пропустим молча).

> **Зачем:** `ledger-rollup.sh month` сворачивает месяц напрямую по дням (осознанно, `CONCEPT-night-cycle.md §5`) — качественные ответы этой недели (retro/carry-over/R-вердикт) иначе в месяц не попадают вообще. Одно событие здесь, не дробление по дням.

```bash
WEEK=$(date +%Y-W%V)
EFFECTIVE_MONTHS=$(python3 -c "
from datetime import date, timedelta
import json
monday = date.fromisocalendar(*[int(x) if i==0 else int(x[1:]) for i,x in enumerate('$WEEK'.split('-'))], 1)
months = sorted({(monday + timedelta(days=i)).strftime('%Y-%m') for i in range(7)})
print(json.dumps(months))
")
SUMMARY_JSON="{\"effective_week\": \"$WEEK\", \"effective_months\": $EFFECTIVE_MONTHS, \"what_worked\": <ретро-ответ шага 1, экранированный>, \"what_didnt\": <ретро-ответ шага 1, экранированный>, \"carry_over\": <carry-over-решение шага 1, экранированное>, \"r_verdict\": <3 R-ответа шага 1, экранированные как массив>}"
bash ~/IWE/DS-my-strategy/scripts/ledger-append.sh week "$WEEK" week_summary "$SUMMARY_JSON" week-close
```

### 8. Pending фазы внутри активных РП (B-005)

> **Зачем:** carry-over §1 Части А работает на уровне РП (status: in_progress → перенос). Pending **фазы** внутри Ф-таблиц context-файлов могут потеряться: если родительский РП в `in_progress` — pending-фаза не выделяется автоматически; если родительский ушёл в `done` — фаза теряется вместе с context-файлом. Пилот уже свободен — вместо живого решения (a/b/c) агент **логирует кандидатов** в WeekReport секцией «Pending-фазы — требует внимания», пилот разбирает при следующем открытии.

```bash

```

Скрипт обходит все `{{WORKSPACE_DIR}}/{{GOVERNANCE_REPO}}/inbox/WP-*.md` со `status: in_progress` (или без явного status), извлекает строки Ф-таблицы со статусом `⏳ pending` / `pending`, выводит сводку формата:

### 9a. Сверка журнала гипотез (LPF, WP-496)

> Регламент: `memory/lpf-hypothesis-log.md`. Журнал: `{{GOVERNANCE_REPO}}/current/hypotheses-log.md`.

2. Для каждой найденной записи: сверить критерий фальсификации с доступной фактурой (коммиты недели, `domain_event`, инфраструктурные логи, факты из статусов §9-10 этого протокола).
3. Предложить вердикт: подтверждена / опровергнута / частично подтверждена / неприменимо (если условие критерия физически не выполнено — например, зависимый артефакт не был доставлен — гипотеза не проверяема, не «опровергнута»).
4. Записать вердикт **новой** записью в конец журнала со ссылкой на исходную (`Сверка H-NNN`) — пилот уже свободен, финальное утверждение вердикта откладывается на его следующий разбор (пометить `pending_pilot_confirm: true`). Исходную запись не редактировать.
5. Для каждого вердикта — явное действие-кандидат (обновить уверенность на будущее / добавить шаг в чек-лист / завести РП / зафиксировать кандидат в паттерн). Вердикт без действия = «повисший», отметить явно. **Блокировка снята сознательно (code review, 2026-07-30-11):** раньше «не закрывать неделю с повисшими вердиктами» — но финальное утверждение вердикта решение пилота (см. п.4), а он уже свободен в Части Б; блокировать агента ожиданием решения, которое он не уполномочен принять сам, бессмысленно — вместо этого повисший вердикт просто виден в WeekReport для разбора при следующем открытии.
6. Если сверенных записей нет — пометить явно «сверка гипотез: 0 записей с наступившей датой» в WeekReport (не пропускать шаг молча).

### 13. Закоммитить governance-репо

> **Защита от гонки параллельных сессий (WP-484 Ф4b).** Week Close — долгая (~20 мин без пилота) операция; за это время параллельные агентские сессии (Kimi/другие) гарантированно продолжают коммитить в тот же репозиторий (найдено 19.07: финальный коммит пришлось перезапускать 3 раза вручную). `week-close-commit-guard.sh` оборачивает commit+push тем же принципом, что `git-dirty-guard.sh` уже даёт открытию дня: `pull --rebase --autostash` перед стейджингом, retry (до 3 попыток) при отклонённом push, коммитит и пушит ТОЛЬКО переданный pathspec — независимо от того, что успело прилететь на origin между попытками.

```bash
cd {{WORKSPACE_DIR}}/{{GOVERNANCE_REPO}}
git status --short
# НЕ git add -A/git add ./git add -u — AGENTS.md CRITICAL (может захватить работу других агентов)
# Файлы, изменённые в шагах 4-12 (в массив для pathspec):
WC_FILES=(<каждый файл явным путём: WeekPlan, WeekReport, WP-REGISTRY, inbox/WP-*.md и т.д.>)
bash {{IWE_SCRIPTS}}/week-close-commit-guard.sh "$(pwd)" "week-close: W{N} итоги q:{score}" "${WC_FILES[@]}"
```

Exit 0 — закоммичено и запушено (возможно после retry). Exit 1 — нечего коммитить (уже сделано на предыдущей попытке этого же шага). Exit 2 — реальный конфликт после исчерпанных попыток или ошибка окружения → разобраться вручную (`git status`, `git log --oneline -5`), не игнорировать.
