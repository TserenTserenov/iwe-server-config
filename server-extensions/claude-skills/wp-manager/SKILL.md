# /wp-manager — Менеджер РП (v0)

> Метод — `DS-my-strategy/inbox/WP-626/Ф3/manager-method-draft.md`; права — `Ф2/role-and-rights-draft.md`; контракт журнала — `Ф4/state-contract-v0-draft.md` с редакцией `Ф6/revision-2-fixes.md`; сборка команды — `Ф5/team-assembly-draft.md`. Статус навыка `experimental`: учебный прогон (РП-626 Ф8) ещё не пройден.

## When to use

Пилот поручает вести РП с готовым описанием: «веди РП-N», «Менеджер, веди РП-N», «продолжи прогон РП-N». Не для одной фазы и не для РП, описание которого не прошло проверку «описание готово» (тогда — конвейер подготовки РП-503).

## Нерушимые правила

1. **Журнал пишет только программа.** Любое событие — через `python3 scripts/wp-run-journal.py append …`. Файлы папки прогона (`events.jsonl`, `lease.json`, `protected/`, `views/`) руками не трогать.
2. **Ответ пилота не записывать.** Ответ попадает в журнал только командой `ingest-answers` из ящика ответов; ящик заполняет автоматическая проверка на сообщение пилота. Пилот отвечает в чате строкой «<номер запроса>: да» / «нет» / «вариант N».
3. **Отказ программы — не препятствие для обхода.** Код 3 означает, что право не позволяет. Нужно вынести вопрос пилоту, а не переформулировать решение под другое правило: такую переформулировку найдёт сверка на М4, и она засчитывается нарушением.
4. **Всё — в ветке прогона.** Результаты фаз и записи прогона идут в ветку `run/<run_id>`. В главную ветку — ничего, её сливает пилот после приёмки. Ничего не удалять: откат — новая попытка или обратный коммит в ветке прогона.
5. **Сначала событие, потом действие.** Перед запуском исполнителя, публикацией, письмом и сообщением пилоту записывается событие; ключ повтора `<run_id>#<seq>` уходит с действием (в строку коммита, `--delivery-id` письма, имя сессии исполнителя).
6. **Не исполнять фазы самому и не проверять то, что назначал.**

## Algorithm

Один вызов навыка — один или несколько тактов; каждый такт — один переход главного конвейера.

### Такт

Каждый такт — один переход главного конвейера:

1. `lease --holder <id сессии>` — взять или продлить аренду; номер эпохи использовать во всех командах такта.
2. `ingest-answers` — забрать ответы пилота.
3. `state` — где прогон: этап, статусы фаз, открытые вопросы, расход, `stop_due`, `all_blocked`.
4. Сделать один шаг по разделу «Этапы» и записать его событием.
5. Если ждём пилота или исполнителя — сказать пилоту, что именно ждём, и закончить такт.

### Этапы (метод Ф3)

**М0 Приём.**
1. Проверить «описание готово»: восемь пунктов плана РП-626 §2.1, у каждой фазы — система, функциональная часть, вид результата (ECO.ARCH.003).
2. Проверить «прогон готов»: доступы, бюджет, условия остановки, предустановка, сухой прогон.
3. Если хоть одна проверка не прошла — `run-stopped` с перечнем недостающего.
4. Если обе прошли — `create`.

**М1 План.**
1. Составить граф фаз (зависимости, `budget_min`, класс И/Ф/Ц) и исполнителей по правилам сборки.
2. Положить карточку `cards/R-plan.md`, затем `pilot-requested`.
3. После ответа пилота — `plan-revised` с `approval_request_id`.

**М2 Ход по фазам** (для каждой готовой фазы):
1. `phase-transitioned` → `ready`.
2. Решение П2 о выборе исполнителя — `decision-recorded`.
3. `phase-assigned` с входами и их отпечатками.
4. Запуск исполнителя.
5. `artifact-submitted` по заявке сдачи.
6. `phase-transitioned` → `checking`.
7. Запуск проверяющего (другой запуск; для кода и фаз Ц — другой вендор) — `verification-recorded`.
8. Переход в `accepted` / `rejected` / `accepted-unconfirmed` / `awaiting-decision`.
9. Выборочная проверка решений `auto` этой фазы — по отбору программы.

**М3 Пересмотр.** После фазы Ф, отказа, блокировки или изменённого допущения сверить допущения. Если план меняется — `plan-revised`; изменение состава фаз или бюджета требует ответа пилота.

**М4 Сверка по смыслу.**
1. Отдельный проверяющий читает принятые фазы и журнал решений.
2. Он заново классифицирует выборку решений (вид и правило).
3. Противоречие или расхождение — вопрос пилоту.

**М5 Итог.**
1. `views`.
2. Отчёт: сделано и не сделано, решения по правам, допущения, расход, три числа ставки H-358, раскрытое зерно отбора.
3. `run-completed`.
4. Статус и закрытие РП меняет только пилот.

## Особые случаи

| Случай | Что делать |
|---|---|
| Пилот отклонил решение | `affected --decision D` → список отката; одна фаза — сам, больше — вопрос пилоту; переходы с `reason: rollback`, `rollback_of: D` |
| Падение, новый запуск | `lease` (новая эпоха) → `state` → фазы `assigned` без сдачи → `unknown` → сверка с исполнителем по ключу попытки |
| Нужен другой РП | `letter-sent` → `scripts/wp-inbox.sh add … --delivery-id <run_id>#<seq>` → фаза `blocked`; круг программа отклонит — тогда вопрос пилоту (П14) |
| `stop_due` или `all_blocked` | остановить новые назначения, вопрос пилоту |
| Код 2 или 4 от программы | не продолжать; показать пилоту вывод программы |

## Чего навык пока не делает (v0)

- Параллельных попыток.
- Запуска себя по таймеру.
- Отправки вопросов в Telegram: на v0 вопросы идут в сессию Менеджера (решение пилота по Ф1).
