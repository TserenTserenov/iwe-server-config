# /wp-manager — Менеджер РП (v0)

> Метод — `DS-my-strategy/inbox/WP-626/Ф3/manager-method-draft.md`; права — `Ф2/role-and-rights-draft.md`; контракт журнала — `Ф4/state-contract-v0-draft.md` с редакцией `Ф6/revision-2-fixes.md`; сборка команды — `Ф5/team-assembly-draft.md`. Статус навыка `experimental`: учебный прогон (РП-626 Ф8) ещё не пройден.

## When to use

Пилот поручает вести РП с готовым описанием: «веди РП-N», «Менеджер, веди РП-N», «продолжи прогон РП-N». Не для одной фазы и не для РП, описание которого не прошло проверку «описание готово» (тогда — конвейер подготовки РП-503).

## Нерушимые правила

1. **Журнал пишет только программа.** Любое событие — через `python3 scripts/wp-run-journal.py append …`. Файлы папки прогона (`events.jsonl`, `lease.json`, `protected/`, `views/`) руками не трогать.
2. **Ответ пилота не записывать.** Ответ попадает в журнал только командой `ingest-answers` из ящика ответов; ящик заполняет автоматическая проверка на сообщение пилота. Пилот отвечает в чате строкой «<номер запроса>: да» / «нет» / «вариант N».
3. **Отказ программы — не препятствие для обхода.** Код 3 означает, что право не позволяет. Нужно вынести вопрос пилоту, а не переформулировать решение под другое правило: такую переформулировку найдёт сверка на М4, и она засчитывается нарушением.
4. **Всё — в ветке прогона.** Результаты фаз и записи прогона идут в ветку `run/<run_id>`. В главную ветку — ничего, её сливает пилот после приёмки. Ничего не удалять: откат — новая попытка или обратный коммит в ветке прогона.
5. **Сначала событие, потом действие.** Перед запуском исполнителя, публикацией, письмом и сообщением пилоту записывается событие; ключ повтора `<run_id>#<seq>` уходит с действием (в строку коммита, `--delivery-id` письма, имя сессии исполнителя).
6. **Не исполнять фазы самому и не проверять то, что назначал.**

## Algorithm

Один вызов навыка — один или несколько тактов; каждый такт — один переход главного конвейера.

### Такт

Каждый такт — один переход главного конвейера:

1. `lease` — взять или продлить аренду; держатель — эта сессия (программа берёт номер из `CLAUDE_CODE_SESSION_ID`, флаг не нужен); номер эпохи использовать во всех командах такта. Папка прогона всегда `<хранилище стратегии>/inbox/WP-N/runs/<run_id>`, другую программа не примет; прогон привязан к машине, где создан.
2. `ingest-answers` — забрать ответы пилота.
3. `state` — где прогон: этап, статусы фаз, открытые вопросы, расход, `stop_due`, `all_blocked`.
4. Сделать один шаг по разделу «Этапы» и записать его событием.
5. Если ждём пилота или исполнителя — сказать пилоту, что именно ждём, и закончить такт.

### Этапы (метод Ф3)

**М0 Приём.**
1. Проверить «описание готово»: из репозитория управления запустить `scripts/check-wp-readiness.py --wp N` и прочитать его последнюю строку. «пробелов N» или «не идёт к Менеджеру РП» (у РП нет отметки `manager: candidate`) — `run-stopped` с перечнем из вывода программы; «готово» — идти дальше. Программа сама сверяет отпечаток допуска (`manager_admission.contracts_sha256`) и при заданной области прогона (`run_scope`) проверяет договоры только её фаз; у каждой фазы нужны оценка и потолок (`ceiling`), без потолка договор неполон. Права в договоре только повышают таблицу П1–П19 из журнала (журнал — единственный источник таблицы). Расхождение имён полей или прав с методом — письмом в ящик РП-503, навык его не правит. Восемь пунктов плана РП-626 §2.1 и смысловую проверку двумя проверяющими выполняет конвейер РП-503 (навык `/wp-prepare`); здесь достаточно записи допуска и строки «готово».
2. Проверить «прогон готов»: доступы, бюджет, условия остановки, предустановка, сухой прогон.
3. Если хоть одна проверка не прошла — `run-stopped` с перечнем недостающего.
4. Если обе прошли — `create --run-dir … --wp N --description-ref <коммит:путь>`, затем создать ветку `run/<run_id>` (run_id = имя папки прогона) от свежей `origin/main` и отправить её: `git push origin run/<run_id>`. Все результаты и записи прогона идут только в эту ветку; запускатель исполнителей РП-530 дописывает в неё же (ответ РП-530 на И-6, 25.11). Ключ повтора для запуска исполнителя — `<run_id>#<seq события phase-assigned>`, в коммит — строкой «Run-Event: …».

**М1 План.**
1. Составить граф фаз (зависимости, `budget_min`, класс И/Ф/Ц) и исполнителей по правилам сборки. Зависимость от фазы другого РП (вид `WP-N/ФM`) в `deps` не класть: журнал отвергает любую неизвестную зависимость («depends on unknown»); до решения пилота (вопрос записан в карточке РП-626) такой договор останавливает приём на М0 (`run-stopped`). `budget_min` берётся как потолок фазы из договора (часы) × 60 — это гипотеза РП-626 Ф8 из письма РП-503 И-4, её проверяет учебный прогон; в метод Ф3 она входит только после «да» пилота.
2. Положить карточку `cards/R-plan.md`, затем `pilot-requested` с полем `action` — на какое действие просим согласия (`{"type": "plan-revised", "version": 1}`; для перехода фазы — `type`, `phase` и `to`; для назначения — `type` и `phase`). Одно «да» разрешает ровно это действие один раз; «вариант N» согласием на действие не считается. Карточку после вопроса не менять.
3. После ответа пилота — `plan-revised` с `approval_request_id`.

**М2 Ход по фазам** (для каждой готовой фазы):
1. `phase-transitioned` → `ready`.
2. Решение П2 о выборе исполнителя — `decision-recorded`.
3. `phase-assigned` с входами и их отпечатками (`inputs`, не пусто), версией договора фазы (`contract_version`) и потолком (`ceiling`) из договора. Пустое поле журнал отклоняет с перечнем недостающего: уточнить договор, не подставлять своё.
4. Запуск исполнителя. Договор фазы передать ссылкой «коммит:путь + номер фазы», не пересказом.
5. `artifact-submitted` по заявке сдачи, с `contract_version` из неё. Журнал сверяет её с версией, назначенной текущей попытке; сдача под номером старой попытки или с другой версией — отказ, фаза остаётся назначенной, та же попытка сдаёт заново по назначенной версии договора.
6. `phase-transitioned` → `checking`.
7. Запуск проверяющего (другой запуск; для кода и фаз Ц — другой вендор) — `verification-recorded`.
8. Переход в `accepted` / `rejected` / `accepted-unconfirmed`. Фаза класса Ц: карточка решения проходит проверку → `awaiting-decision` → `pilot-requested` по решению → `decision-recorded` со статусом `confirmed` → `accepted`.
9. Выборочная проверка решений `auto` — список даёт команда `sample` (Менеджер его не составляет).

**М3 Пересмотр.** После фазы Ф, отказа, блокировки или изменённого допущения сверить допущения. Если план меняется — `plan-revised`; изменение состава фаз или бюджета требует ответа пилота.

**М4 Сверка по смыслу.**
1. Отдельный проверяющий читает принятые фазы и журнал решений.
2. Он заново классифицирует выборку решений (вид и правило).
3. Противоречие или расхождение — вопрос пилоту.

**М5 Итог.**
1. `views`.
2. Отчёт: сделано и не сделано, решения по правам, допущения, расход, три числа ставки H-358, раскрытое зерно отбора.
3. `run-completed`.
4. Статус и закрытие РП меняет только пилот.

## Особые случаи

| Случай | Что делать |
|---|---|
| Пилот отклонил решение | `affected --decision D` → список отката; одна фаза — сам, больше — вопрос пилоту; переходы с `reason: rollback`, `rollback_of: D` |
| Падение, новый запуск | `lease` (новая эпоха) → `state` → фазы `assigned` без сдачи → `unknown` → сверка с исполнителем по ключу попытки |
| Нужен другой РП | `letter-sent` → `scripts/wp-inbox.sh add … --delivery-id <run_id>#<seq>` → фаза `blocked`; круг программа отклонит — тогда вопрос пилоту (П14) |
| `stop_due` или `all_blocked` | остановить новые назначения, вопрос пилоту; `run-stopped` не снимает с сессии ограничений Менеджера — их снимает только `run-completed`; после остановки ограничения снимает пилот сам (удаляет отметку сессии `~/.iwe-runtime/wp-manager/sessions/<номер сессии>.json`), Менеджер этого не делает и не просит |
| Код 2 или 4 от программы | не продолжать; показать пилоту вывод программы |

## Чего навык пока не делает (v0)

- Параллельных попыток.
- Запуска себя по таймеру.
- Отправки вопросов в Telegram: на v0 вопросы идут в сессию Менеджера (решение пилота по Ф1).
