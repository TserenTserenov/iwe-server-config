# /visionary — Визионер, ступень 1 (только автор)

> **Scope:** заготовка выдачи на завтра для утреннего сообщения Камердинера (режим `prepare`, вызывается на закрытии дня), фокус дня по вопросу пилота в беседе (режим `focus`), запись отклика и исходов проб (`outcome`), месячное мерило (`stats`).
> **Not in scope:** писать человеку в Telegram самому — утро ведёт Камердинер (РП-623, решение пилота 21.11.2026), он показывает выдачу и возвращает отзыв кнопками; обзор новостей; пересборка рекомендации Портного; ступени 2–3 (РП-622 Ф4–Ф5).
> **Role:** Визионер (DP.ROLE.127). Обещание — DP.SC.231. Сценарии С1, С4, С5а, С5б, С6 — в паспорте роли. Контракт выдачи Камердинеру (версия 2) — карточка РП-622, Ф2 П1.

## When to use

- Закрытие дня вызывает режим `prepare` на завтрашнюю дату через расширение `extensions/day-close.after.visionary.md` (С1). Это **заготовка, не показ**: предложения в беседе не показываются и доставкой не считаются; утром их показывает Камердинер.
- Пилот спрашивает «что я могу сегодня сделать по-новому?» (С4) — режим `focus`, ответ в этой беседе. Сюда же «подробнее» по строке утреннего сообщения: показать полное предложение по номеру пробы из журнала.
- Пилот сообщает отклик или исход пробы с номером (С6) — режим `outcome`.
- Пилот или подсчёт ставки H-353 спрашивает мерило за месяц — режим `stats`.

## Preconditions

1. **Журнал проб пишется в изолированную копию репозитория стратегии этой беседы** (главная копия заморожена). `J_REPO` — путь из поля `isolated_worktree:` отметки открытой сессии этой беседы (`~/IWE/.iwe-runtime/sessions/<агент>-<id>.open`); если сессии с изолированной копией нет — открыть её штатно (`session-guard.sh open --isolate`, из папки репозитория стратегии). Запись публикуется тем же путём, что остальные правки беседы (коммит в изолированной копии и `ds-publish.sh`), до её закрытия.
2. Программа журнала: `JOURNAL="$HOME/IWE/DS-my-strategy/scripts/visionary-journal.py"` — вызывается всегда с `--repo "$J_REPO"`.
3. **Запрещено** писать человеку самому: ни `send_telegram_message`, ни служебный канал сигналов IWE (`iwe-tg`, `lib/telegram.sh`), ни другой путь. Утром человеку пишет только Камердинер.

## Algorithm

Шаги 1–5 общие для `prepare` (дата `D` = завтра) и `focus` (дата `D` = сегодня). Дальше — Шаг 6П для `prepare` или Шаги 6–7 для `focus`.

#### Шаг 1 — Собрать внутреннее

Input: дата `D`, файлы пилота.
Action: прочитать (только нужное, выдержками):
- Персона: `~/IWE/PD-persona/Lifework/` (миссия, личный устав, профессиональные принципы), `~/IWE/PD-persona/masteries.yaml`;
- дела: план на `D` — для `focus` раздел плана из DayPlan (`DS-my-strategy/current/DayPlan <дата>.md`); для `prepare` — выбор на завтра, названный на закрытии дня, и незакрытое из сегодняшнего плана; направления недели (`current/WeekPlan W*.md`, последний), РП P1 в работе (`docs/WP-REGISTRY.md`);
- затруднения: `docs/Dissatisfactions.md` (открытые), заблокированные РП (🚧 в реестре), уроки памяти за 7 дней (`memory/lessons_*.md`, по дате в имени или frontmatter);
- узкое место и материал дня Портного — **файловый вход ступени 1**: `panel/<D>.md` (узкое место, задание) и `guide/<D>.md` (материал, упражнение) личного руководства. Где читать: `~/IWE/DS-personal-guide/` на диске; папки нет (сервер) — через GitHub: `gh api "repos/TserenTserenov/DS-personal-guide/contents/guide/<D>.md" -H "Accept: application/vnd.github.raw"`. Руководство на завтра собирается ночью, поэтому для `prepare` файлов на `D` обычно ещё нет — это штатно (см. ниже);
- изменения внутреннего: закрытые за 7 дней РП (✅ в реестре со свежей датой), итог Наставника ИИ, если есть, закреплённые пробы (Шаг 3).
- **сверка руководства с решениями пилота:** задание дня из `panel/<D>.md` (если есть) сравнить с более поздними решениями пилота — раздел «Не берём» плана недели, отложенные и замороженные РП в реестре. Задание касается отложенного РП → пробу к нему не предлагать; запись во входящие РП-521 (`wp-inbox.sh`, выжимка: дата, задание, решение пилота с источником). В `focus` на экране одна строка «задание руководства — РП-N, ты отложил его до <срок>; записал во входящие руководства» — только после успешной записи.
Output: краткий конспект «дела дня, затруднения, узкое место, что нового во мне, расхождение руководства с планом (если есть)».

**Нет файлов руководства на `D`** → предложения **остаются**, в каждом «что изучить: нет — <причина>» (поле `study_absent_reason`: «руководство на <D> собирается ночью» / «вход руководства недоступен: <что не прочиталось>»; если для пробы получен номер рекомендации РП-521 (`recommendation_id`, Шаг 5, действие 2), «собирается ночью» не писать: «цитаты руководства нет, метод взят из рекомендации РП-521»). Свой учебный совет вместо материала Портного не придумывать. Ноль предложений — только по правилам Шага 4 (решение РП-622 Ф2 П4, 21.11.2026; паспорт роли DP.ROLE.127).

#### Шаг 2 — Собрать внешнее

Input: конспект Шага 1, раздел «Мир» последнего DayPlan.
Action:
- **внешнее общее:** ссылки и вывод раздела «Мир» DayPlan;
- **внешнее личное:** 1–3 веб-поиска по двум-трём главным делам или затруднениям `D` (что нового в моделях, инструментах, методах для этого дела за последние недели). У каждой находки — ссылка и дата публикации; находка без даты или ссылки отбрасывается.
- **свежесть:** находка старше 30 дней — не «что изменилось», отбрасывается, даже если подходит к делу; в `focus` на экране одной строкой сказать, что такая находка была и почему не показана.
- **подтверждение:** изменение инструмента или модели, найденное в сторонней сводке, сверить с официальным источником (список изменений, документация, сообщение производителя). Не подтвердилось — не предлагать как факт. Основание — официальная ссылка; дата из сводки — с пометкой, откуда она. Если источник говорит, чего изменение НЕ покрывает, — сказать это в «Что изменилось».
- **версия у пилота:** проба зависит от версии инструмента → проверить установленную версию командой (`<инструмент> --version`) и записать в пробу, что проверено и где; проверить нельзя — «проверь версию».
- **«Мир» не натягивать:** новость из раздела «Мир», которая не относится ни к одному делу пилота, не превращать в предложение.
Output: список находок «что изменилось — ссылка — дата — вид (внешнее общее / внешнее личное)» и отброшенные с причиной.

#### Шаг 3 — Память проб

Input: журнал.
Action: `python3 "$JOURNAL" --repo "$J_REPO" history --days 60`.
Output: открытые пробы, отклонённые (не предлагать снова без нового основания — новое основание = другая ссылка или более поздняя дата, чем у отклонённой; «не сегодня» — не отказ, такую идею можно предложить снова), закреплённые (это «новое во мне» для Шага 4).

#### Шаг 4 — Сопоставить и отобрать 0–3

Input: Шаги 1–3.
Action: для каждой находки (и для каждого изменения внутреннего) спросить: к какому делу пилота она относится и что конкретно в день `D` можно сделать иначе? Оставить не больше трёх **по убыванию важности** (первое — главное: при нехватке места Камердинер оставит только его), где есть всё: изменение с основанием, дело, проба на настоящей задаче, признак успеха и «что изучить и потренировать» — материал Портного цитатой либо пометка его отсутствия с причиной (Шаг 1).
- **Проба** — конкретное действие, которое пилот выполнит без догадок (что запустить, где). **Признак успеха** — наблюдаемый в ходе самой пробы и доказывающий именно изменение, а не побочный эффект: если тот же исход может дать что-то другое, в пробу входит контроль, который это исключает.
- **Шаги пробы против наших проверок (VIS-20261120-1, 20.11):** если в пробе или её контроле есть команды (git, оболочка, установка), до предложения сверить каждую с проверками опасных команд среды (`.claude/hooks/destructive-guard.sh` и соседние проверки в `.claude/hooks/`). Команда запрещена → выбрать проверку, которую наши правила пропускают, или не предлагать пробу. Если наша проверка запрещает то же, что новое изменение инструмента, это уже ответ на вопрос «упрощать ли нашу проверку» — без пробы.
- **Выбор цитаты (если руководство на `D` есть):** дословный фрагмент упражнения, вопроса для рефлексии или раздела «На практике» из `guide/<D>.md`, применимый к пробе; принцип без действия — только если упражнения нет. Без обрезки, меняющей смысл. Перед записью сверить дословность (`grep -F` по файлу на диске или по тексту, полученному через GitHub).
Output: 0–3 предложения. **Ноль** — честный ответ с причиной: нового с основанием нет, или без материала руководства нельзя сформулировать осмысленную пробу (С5а). Нет дел и целей (пустой план и нет РП в работе) — С5б: в `focus` вместо предложений вопрос пилоту о его деле, ничего не записывать; в `prepare` — ноль с причиной «нет дел на <D>».

#### Шаг 5 — Записать предложения

Input: предложения Шага 4.
Action: каждое предложение записать до показа или выдачи: поля — в файл (инструментом записи файлов, во временную папку беседы), затем `python3 "$JOURNAL" --repo "$J_REPO" propose --json <файл>`; поля: `date` (= `D`), `what_changed, basis, basis_date, source (internal|external_common|external_personal), work, why, trial, success_sign` и либо `study_origin` + `study_quote` (файл руководства с полной датой `DS-personal-guide/guide/ГГГГ-ММ-ДД.md` и дословная цитата), либо `study_absent_reason`; необязательное `recommendation_id` — номер рекомендации РП-521, только если РП-521 выдал его для этой пробы (текст одной строкой до 80 знаков, без пробелов по краям и без невидимых символов; число или пустое значение программа отвергнет; номер не придумывать и не угадывать — нет номера, поля нет; он копируется в строку выдачи); необязательное `method_line` — короткая версия действия метода из ответа РП-521 (поле `short_action`) дословно одной строкой, только вместе с `recommendation_id`; когда оно ставится, а когда нет — правило в действии 2 этого шага ниже; программа кладёт его в пункт выдачи ключом `method_line`, внутрь `recommendation` текст не попадает; утром строку показывает Камердинер (РП-623), не длиннее 80 знаков (РП-623 И-23); сам текст не сокращать, не чистить и не пересказывать (решение пилота 27.11, РП-521 И-25).
 Номер входит в само предложение, к уже записанной пробе его не добавить, поэтому запрос рекомендации у РП-521 идёт до записи, по такому порядку (решение пилота 26.11, схема 1а; ключ запроса — номер пробы):
   1. Взять номер: `python3 "$JOURNAL" --repo "$J_REPO" new-id --date <D>` (например `VIS-ГГГГММДД-3`). Дубль проверять не вручную: если такое же предложение уже записано, программа на шаге 4 откажет и назовёт записанный номер.
   2. Запросить рекомендацию под этим номером. Предусловие: значение `person` (идентификатор человека в реестре РП-521). Для пилота это `pilot-1` (ответ РП-521 И-20 от 26.11; то же значение, что у Камердинера, иначе окно 7 дней и повтор ключа не сойдутся). Для другого человека значение не назначено: запрос не выполнять, предложение записать без `recommendation_id`, в отчёт беседы одной строкой «запрос рекомендации не выполнялся: person для этого человека не назначен»; `study_absent_reason` для этого не использовать: оно исключает цитату руководства и описывает отсутствие материала, а не номера. Значение есть — вызвать по ssh (внешние кавычки одинарные, `--db` стоит до подкоманды, скрипт запускается файлом, не как пакет): `ssh tsekh-1 'python3 ~/.local/share/iwe/recommendation-registry/code/generator/recommendation_flow.py --db ~/.local/share/iwe/recommendation-registry/registry.db request --snapshot ~/.local/share/iwe/recommendation-registry/catalog.json --person <person> --request-id <номер из шага 1> --params-json "{\"case\":\"<дело>\",\"probe\":\"<проба>\",\"date\":\"<D>\"}"'`. `--slot` и `--slot-cut-date` всегда опускать на всех повторах одного ключа (ответ РП-521 И-20): на выбор метода они не влияют, ответ придёт с пометкой `slot_unknown` — это норма; поле, однажды опущенное для ключа, не добавлять (иначе `request_conflict`); повтор того же ключа допустим только с тем же набором параметров. Шаблон проверен только для значений из букв, цифр, пробелов и знаков `. , : -`; если в деле или пробе есть другие знаки (апостроф, `$`, обратная кавычка, `\`, кавычка), шаблон не применять, запрос не выполнять, параметры не менять, ограничение записать в отчёт беседы (передачу произвольного текста — отдельная доработка, под S-33). Ответ — одна строка JSON: `recommendation_ref` (вид `rec_…`) копируется в `recommendation_id`. Строка метода (`method_line`) ставится, только если одновременно: получен `recommendation_ref` вида `rec_…`, который копируется в `recommendation_id` этого же предложения; `short_action` — строка, в которой есть хотя бы один непробельный знак, длиной не больше 80 знаков, если пробелы подряд считать за один (так считают сервис РП-521 и читатель Камердинера; сам текст при этом не меняется); в `flags` нет `material_changed` и `recommendation_not_live`. Тогда `method_line` = `short_action` дословно: края не обрезать, пробелы не сжимать, не пересказывать. Во всех остальных случаях строки метода нет: поля `short_action` в ответе нет, `null`, пустая строка или одни пробелы, не строка, длиннее 80 при таком подсчёте, пришла пометка `material_changed` или `recommendation_not_live` (рекомендация истекла или не прошла проверку: Камердинер подтвердить её показ не сможет; пометка главнее текста), нет такого `recommendation_ref` (поля нет, `null`, другой вид). `next_action` и `criterion` в `method_line` не класть никогда, независимо от их длины, и как замену пустому `short_action` тоже. Пока РП-600 не написал короткие тексты, `short_action` пустой у всех методов — это норма: утро идёт без строки метода и без подтверждения показа. `short_action` длиннее 80 при таком подсчёте — предложение без `method_line`, строка в отчёт беседы и запись во входящие РП-521 (нарушено их обещание «одна строка до 80»). Отдельный `show` не нужен, запрос сам ставит отметку проверки. Подтверждение показа (`confirm`) в навык не входит: после успешной отправки утреннего сообщения его вызывает Камердинер (РП-623). Исход: (а) номер получен — брать его; (б) РП-521 ответил отказом с кодом причины — идти дальше без `recommendation_id`, код причины записать в `study_absent_reason`, только если цитаты руководства нет (при цитате руководства поле не использовать: программа отвергнет предложение с обоими; код причины идёт в отчёт беседы); исключение `request_conflict` (тот же `request-id` пришёл с другими данными): остановиться, ключ и данные не менять, сказать пилоту — это нарушение идемпотентности, его нельзя обходить; (в) тайм-аут или неизвестный исход — повторить тот же запрос с тем же `request-id` и теми же данными (повтор безопасен только при полном совпадении всех параметров, включая `--slot` и `--slot-cut-date`: тот же ключ тогда возвращает тот же номер, иначе `request_conflict`) не больше двух раз, затем идти без `recommendation_id`, сохранив `request-id` и весь набор параметров в отчёте беседы (ночной шаг повторит тот же запрос теми же данными; отказ `request_conflict` при повторе — разбор расхождения, не очередной повтор); нового номера пробы при неизвестном исходе не брать.
   3. Записать предложение с полем `expected_trial_id` = номер из шага 1, `recommendation_id` из ответа (если есть) и `method_line` — только по правилу действия 2. Если программа отказала именно из-за `method_line` (пробелы по краям, перенос, невидимый символ; отказ ничего не записал) — повторить запись один раз с теми же полями без одного `method_line`, строка в отчёт беседы и запись во входящие РП-521; при тайм-ауте или другом отказе так не делать.
   4. Отказ записи (программа сначала ищет такое же предложение, потом проверяет номер, поэтому дубль и «занятый номер» не путаются): «is not the next number» (номер успел занять другой) — взять новый номер ОДИН раз (шаги 1–3 заново; запрос РП-521 уйдёт под новым номером, поэтому у старого ключа останется неиспользованная рекомендация), записью во входящие РП-521 назвать брошенный ключ; второй такой отказ подряд — остановиться и сказать пилоту, цикл не продолжать. «already recorded as VIS-…» — такая же проба уже записана: использовать названный номер, предложение заново не писать, рекомендацию, полученную под другим номером, не присоединять (назвать её во входящие РП-521 как брошенную).
   5. Ночной шаг (П6) пока не существует; когда он появится, он не повторяет запись предложения, а повторяет запрос рекомендации с тем же `request-id` и теми же данными и дописывает номер отдельным событием журнала (программа его ещё не умеет, правка — П6, по разрешению пилота). Строку метода при повторе вычислять заново по ответу повтора по правилу действия 2; значение из прежнего ответа не переносить.
   Для внешнего источника `basis` — ссылка `http(s)://`. Отказ (код 1) по полям — исправить поля этого предложения и повторить, не обходить; повтор без `expected_trial_id` уже записанного предложения вернёт его прежний номер.
Output: номера проб.

#### Шаг 6П — Выдача Камердинеру (только `prepare`)

Input: номера Шага 5 в порядке важности.
Action:
1. Для каждого предложения — строка для экрана: до 60 знаков, одна строка, начинается с действия («Попробовать…», «Запустить…»); без номера пробы и ссылок — их Камердинер берёт из выдачи сам.
2. Записать выдачу: файл `{"date": "<D>", "items": [{"trial_id": "VIS-…", "line": "…"}, …]}` (пустая выдача — `{"date": "<D>", "items": [], "zero_reason": "<причина>"}`), затем `python3 "$JOURNAL" --repo "$J_REPO" prepare --json <файл>`. Программа сама берёт из записей проб источник, ссылку «подробнее» и признак рекомендации; проверяет число, длину строки, дату и что проба не отклонена. Вернёт номер выдачи `PREP-ГГГГММДД-N`.
3. Проверить чтение так, как его увидит Камердинер: закоммитить журнал в `J_REPO`, затем `python3 "$JOURNAL" --repo "$J_REPO" issue --date <D> --rev HEAD` — в ответе тот же номер выдачи и те же строки, без поля `unavailable`.
4. Опубликовать вместе с остальными правками беседы **не позже 03:00 по местному времени** (копия на сервере догоняет главную в пределах часа, Камердинер шлёт с 05:00).
5. Пилоту — одна строка без содержания предложений: «Заготовка Визионера на <D> готова: N предложений (<номер выдачи>); утром их покажет Камердинер». Ноль — «Заготовка на <D>: предложений нет — <причина>».
Output: выдача в журнале и опубликована.

### Режим `outcome` (С6)

Input: номер пробы и слово пилота (в беседе) или отзыв кнопкой из журнала утра Камердинера.
Action: сопоставить слово с шагом и записать `python3 "$JOURNAL" --repo "$J_REPO" mark <номер> <шаг> [--result success|partial|fail] [--note "<заметка>"] [--evidence "<свидетельство>"]`:
- отклик на предложение: «полезно» / 👍 → `useful` (оценка совета, статус пробы не меняет); «не нужно» / 👎 → `declined` (не предлагать снова без нового основания); «не сегодня» → `postponed` (не отказ, проба может быть принята позже);
- исход: «принимаю» → `accepted`; «попробовал: …» → `outcome` с `--result` по словам пилота (неясно — спросить один раз); «закрепляю» → `fixed`; «не закрепляю» → `not_fixed`; «эффект: …» → `effect` с `--note`.
- **Отзывы Камердинера:** когда журнал утра Камердинера (РП-623 Ф5) содержит показ и отзывы, перенести их при следующей подготовке: показ → `focus --date <дата> --count <N> --ids <показанные> --shown-in kamerdiner:<номер выдачи>:<сообщение>`; кнопки — как отклик выше. Повтор переноса не дублирует записи.
- **Свидетельство применения (РП-521 И-12, решение пилота 24.11):** у шагов `accepted` и `outcome` — `--evidence` с тем, что человек сделал и когда, одной строкой до 200 знаков со ссылкой на подтверждение (коммит, запрос на слияние, запись); берётся из слов пилота или отчёта, не выдумывается. Свидетельство записывается вместе с самим шагом: точный повтор вернёт «already recorded», другое свидетельство для уже записанного шага программа отвергнет (код 1), поэтому для `accepted` без свидетельства приложить его к шагу `outcome`. Хранит свидетельства у карточки метода РП-608, Визионер только принимает и пишет в свой журнал.
- **Отметка «рекомендация взята» для РП-521** — только по `accepted` пробы, у которой в выдаче была ссылка на рекомендацию; не по «полезно». Способом РП-521 после его Ф19; до того — только запись в журнале.
Программа сама держит порядок (нельзя «закрепляю» до «попробовал»); отказ — сказать пилоту, какого шага не хватает. Коммит и публикация — как в Шаге 7.
Output: строка в журнале; «already recorded» — повтор, не ошибка.

## Anti-patterns

- Обзор новостей вместо 0–3 предложений с пробой.
- Учебный совет Визионера вместо материала Портного; пересказ цитаты своими словами.
- Ноль предложений только потому, что руководства на дату ещё нет.
- Показ заготовки `prepare` в беседе как фокуса дня; запись `focus` для заготовки.
- Сообщение человеку в Telegram от Визионера.
- Отметка «рекомендация взята» по кнопке «полезно».
- Повтор отклонённого предложения без нового основания.
- Предложение без ссылки и даты основания.
- Запись в главную копию репозитория стратегии.
