# /project-analysis — Анализ проекта

> # see VR.SC.007, VR.R.002
>
> **Scope:** быстрый анализ одного проекта по блоку «дела и проекты» Чек-листа защиты нужного этапа; выход — уровни, три пробела, направления.
> **Not in scope:** блок «про себя» и ступень (это диагностика, `/diagnose`); запись факта пути (РП-522); исправление пробелов; полная проверка по эталону (`/verify`).
> **Role:** VR.R.002 Аудитор — проверка полноты по чек-листу.

## When to use

- Участник S2/S3 перед защитой проверяет свой проект сам.
- Наставник готовится к разговору с участником (рядом с `/mentor-participant-brief`, не внутри него).
- Автор быстро анализирует свой РП или проект.

## Preconditions

1. **Бланк доступен.** Бланк этапа и рубрика уровней читаются из `MimEcoSys/Programs`: `personal-development/practicums/S{0..3}/defense-checklist.md` и раздел «Чек-лист защиты — общий каркас S0–S3» в `personal-development/practicums/README.md`. Локальная копия — `~/IWE/Programs/`; перед чтением — `scripts/iwe-safe-pull.sh ~/IWE/Programs`. Бланк недоступен → сообщить и не проводить анализ по памяти.
2. **Этап назван.** Этап S0–S3 задаёт заказчик. Не назван → спросить; не угадывать по проекту.
3. **Материал проекта есть.** Текст, карточка проекта (для РП автора — `DS-my-strategy/inbox/WP-N/WP-N.md`, только открытые фазы), для S2–S3 — репозиторий ИИ-среды. Материала нет → все пункты «неизвестно» и список вопросов для добора.

## Algorithm

### Step 1 — Шаг 0: тип результата

Input: материал проекта.
Action: через `/artifactor` (или его Шаг 2.0 и 2.1 вручную) ответить на два вопроса: результат проекта — действующая система или документ; кто что производит (связка «документ ↔ производитель»). Другие поля Артефактора не использовать. Тип неочевиден → записать «не определён» — это уже пробел для направления к Артефактору.
Output: строка «Результат: система | документ | не определён; производитель: …».

### Step 2 — Прочитать бланк этапа

Input: этап, свежая копия Programs.
Action: прочитать блок «дела и проекты» бланка этапа (для S2 — блоки «проект» и «ИИ-среда», для S3 — «проекты» и «программа и среда») и шкалу уровней. Пункты не пересказывать и не дополнять своими. Определить объём анализа:
- **один проект** (по умолчанию) — пункты о проекте применяются целиком; пункты о всей программе проектов и о ИИ-среде человека в целом (S2 С1–С5, S3 Р1, Р3–Р7) помечаются «вне анализа одного проекта» и не оцениваются; главное ограничение (S3 Р2) оценивается в границах этого проекта. Исключение: если сам проект — ИИ-среда человека, пункты о среде применяются;
- **S0–S1 — дела недели** — на этих этапах бланк описывает все дела участника, а не проект (проект на S1 необязателен). Проект анализируется как одно из дел: пункты о списке рабочих продуктов по всем делам (S1 Д3) помечаются «вне анализа одного проекта», остальные оцениваются по делам, где проект — главный материал;
- **все проекты** — заказчик просит проанализировать все свои проекты или программу проектов; тогда блок «программа и среда» применяется целиком, а материал — все проекты.
Output: список пунктов с номерами из бланка, пометкой «событие» для пунктов-событий (результат сдан, адресат найден, метод опубликован, предъявление проведено) и пометкой «вне анализа» там, где пункт не применяется.

### Step 3 — Обход пунктов

Input: список пунктов + материал проекта.
Action: по каждому пункту найти в материале свидетельство (что сделано, продукт, адресат, дата) и поставить уровень: неизвестно / 1 «был случай» / 2 «устойчиво» (не меньше трёх недель или двух дел-проектов) / 3 «переносит». Свидетельства нет → «неизвестно», не «нет». Цитировать источник (файл, раздел, дата).
Output: таблица `пункт | уровень | свидетельство | источник`; пункты «вне анализа» перечисляются одной строкой под таблицей.

### Step 3a — Системный срез проекта (любой этап)

Input: материал проекта + бланк S3 (`practicums/S3/defense-checklist.md`, пункты П1–П4).
Action: на этапах S0–S2 дополнительно оценить проект по четырём системным пунктам бланка S3 той же шкалой: П1 адресат и изменение у него, П2 граница (целевая система, окружение, надсистема), П3 цель как договор с адресатом, П4 назначение → функции → устройство. Срез показывает, куда растёт проект; в оценку этапа и в три пробела не идёт. На S3 срез не нужен — эти пункты уже в основной таблице.
Output: таблица «Системный срез (на вырост)» из четырёх строк или пометка «S3 — срез в основной таблице».

### Step 4 — Три пробела

Input: таблица Step 3.
Action: выбрать три пункта с наибольшим отставанием от уровня закрытия (2; для пунктов-событий — 1). При равенстве — пункт, от которого зависят другие (граница и назначение раньше устройства, устройство раньше передач).
Output: три пробела с одной фразой «чего не хватает».

### Step 5 — Направления

Input: три пробела.
Action: по каждому пробелу дать направление «роль + метод», скилл — если у метода есть исполнитель в ИИ-среде заказчика. Таблица соответствий — в VR.SC.007 §«Направление»:

| Пробел | Роль | Метод → скилл |
|---|---|---|
| непонятен результат | Артефактор-Постановщик | постановка задачи → `/artifactor` |
| назначение, граница, устройство, развилка | R5 Архитектор | АрхГейт, ADI-цикл → `/archgate`, `/think` |
| главное ограничение | Аналитик ограничений | пять шагов ТОС → `/bottleneck-pick` |
| этапы и передачи между работами | R29 Декомпозитор | декомпозиция, ВДВ → `/decompose`, `/vdv` |
| проверка готового результата | VR.R.001 Верификатор | верификация по эталону → `/verify` |
| ритм дня и недели, вход в работу, выбор недели, адресат | R1 Стратег | открытие и закрытие дня, план недели, стратегирование → `/day-open`, `/day-close`, `/strategy-session` |
| методы ядра и гигиены саморазвития (зонтик рабочих продуктов, стоп-лист, заметки, изменение стиля, стоп-момент) | Ученик — сам участник | карточка метода в Библиотеке и занятие практикума; скилла нет |

Неполное направление: нет скилла → роль и метод с карточкой в Библиотеке; нет метода → роль и вопрос, метод не придумывать; нет ни роли, ни метода → «без исполнителя»: пробел и вопросы, плюс строка-кандидат в системный набор для автора (РП-385 Ф15.4). Роль не придумывать.
Output: отчёт анализа (формат ниже).

## Формат отчёта

```markdown
# Анализ проекта: <название> · этап <SN> · <дата> · бланк <версия>

Результат: <система | документ | не определён>; производитель: <…>

| Пункт | Уровень | Свидетельство | Источник |
|---|---|---|---|

## Три пробела и направления
1. <пункт> — <чего не хватает> → <роль>, <метод> (<скилл | «скилла нет» | «без исполнителя»>)

## Системный срез проекта (на вырост; в оценку этапа не входит)
| Пункт S3 | Уровень | Свидетельство |
|---|---|---|

Кандидаты в системный набор: <пробелы без исполнителя | «нет»>
```

Отчёт отдаётся заказчику в чат. Сохранять его в проект или двойник — решение заказчика, не скилла.

## Bundled resources

Нет. Эталон признаков и шкала живут в Programs; таблица направлений — в VR.SC.007.

## Anti-patterns

- Держать свою копию пунктов чек-листа в скилле — бланк в Programs единственный источник.
- Ставить «нет» вместо «неизвестно», когда в материале просто не нашлось свидетельства.
- Оценивать блок «про себя» или называть ступень — это диагностика.
- Включать пункты системного среза в три пробела этапа S0–S2 — срез показывает рост, не долг этапа.
- Исправлять пробелы самому вместо направления к роли.
- Придумывать роль или метод, когда их нет, — пиши «без исполнителя».
- Оценивать по одному проекту пункты о всей программе проектов или о среде человека в целом — они «вне анализа одного проекта».

## Verification

```bash
bash .claude/skills/skill-creator/scripts/verify-skill.sh project-analysis .claude/skills
```

Содержательная проверка — прогон на реальном проекте: каждое свидетельство ссылается на источник, каждое направление называет роль из реестра ролей или помечено «без исполнителя».
