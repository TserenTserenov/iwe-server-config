# Protocol Open Extensions (sync) — авторские

> Выполняется в шаге 3 «Sync Gate» § WP Gate перед Ритуалом.
> Автор: Tseren (author_mode). Слой 3 (extensions). Spawn: WP-294 (2026-05-06).

## Цель

При упоминании номера РП — синхронизировать его открытые фазы с тем, что фактически реализовано в связанных РП. Исключить дубликаты работы, ложные блокеры, неверные оценки в Ритуале.

**Архитектурное решение (вариант D):** гибрид детерминированного bundler'а + LLM sub-agent on demand.

## Шаг 3.1 — Bundle

```bash
WP_NUM="<номер РП, упомянутый пользователем>"
bash "$IWE_WORKSPACE/scripts/wp-sync-bundle.sh" "$WP_NUM" > /tmp/wp-sync-bundle-$$.md
BUNDLE_EXIT=$?
```

- Exit 0 → bundle создан, читать его
- Exit 1 → РП не найден → пропустить sync-step, в Ритуале указать «контекст РП не найден, актуализация невозможна»
- Exit 2 → ошибка парсинга → вывести в «Требует внимания», продолжить без sync

## Шаг 3.2 — Чтение bundle

`Read /tmp/wp-sync-bundle-$$.md` — получить:
- Список связанных РП с их статусами
- Drift-сигналы (если есть)
- Рекомендацию bundler'а (тривиально / нужен sub-agent)

## Шаг 3.3 — Решение по веткам

### Ветка A — тривиальный случай

**Условие:** связанных РП ≤ 1 И drift-сигналов нет.

Главный агент применяет правки сам:
- `Read` контекст текущего РП
- Если связанный закрыт и упомянут в открытой фазе → `Edit` для проставления `[x]` и пометки даты
- Иначе → ничего не менять

≤2 минуты, без делегирования.

### Ветка B — нетривиальный (по умолчанию)

**Условие:** связанных РП ≥ 2 ИЛИ есть drift-сигналы.

Делегировать через Task tool sub-agent'у `wp-sync-actualizer`:

```
Task(
  subagent_type: "wp-sync-actualizer",
  description: "Актуализация WP-N",
  prompt: "Номер: WP-N\n\nBundle:\n\n<содержимое /tmp/wp-sync-bundle-$$.md>\n\nВерни unified diff для применения."
)
```

Главный агент:
1. Получает diff в текстовом формате (`---ORIGINAL---` / `---REPLACEMENT---`)
2. Применяет его через `Edit` (по одному блоку)
3. Если sub-agent вернул раздел «Требует внимания» — добавить пункты в «Требует внимания» Ритуала, **не применять автоматически**

### Ветка C — противоречие

Если sub-agent вернул блокирующее противоречие (не применённый diff, только описание) — сразу к Ритуалу с раскрытием конфликта пользователю. **НЕ принимать решение автономно.**

## Шаг 3.4 — Очистка

```bash
rm -f /tmp/wp-sync-bundle-$$.md
```

## Анти-патёрны

- **Запускать sync на закрытых РП** (статус `done`/`closed`) — бессмысленно. Если РП закрыт, sync-step пропускается.
- **Запускать sync несколько раз в одной сессии для одного РП** — bundle стабилен между сообщениями. Если уже запускал в этой сессии — не повторять, использовать кэш в TodoWrite/контексте.
- **Применять diff без `Read` исходного файла** — нарушение Edit tool требований.
- **Делегировать на Opus** — sync = closed-loop (есть YAML + git log как ground truth). Sonnet 4.6 достаточно.

## Замечание о моделях

| Главный агент | Поведение sync-step |
|---|---|
| Haiku 4.5 | Bundle обязателен. Только ветка A (если триггерится). Иначе сразу делегировать B даже при 1 связанном РП. |
| Sonnet 4.6 | Стандартное поведение по веткам A/B/C. |
| Opus 4.7 | Может делать B сам без делегирования (но дорого). По умолчанию — делегировать Sonnet через Task. |

## Связь с другими протоколами

- **DayPlan Gate (шаг 2)** уже выполнен → известно, что РП в плане недели
- **Sync Gate (шаг 3, этот)** — актуализирует контекст
- **Ритуал согласования (шаг 4)** — использует актуализированный контекст для оценки `~Xh` и формулировки «Что осталось»

## Граница ответственности

Этот extension актуализирует **открытые фазы и чекбоксы**. Не меняет:
- `name:` РП (это синхронизация S-14, отдельное правило)
- Стратегические решения, ArchGate, Roadmap
- WP-REGISTRY.md (обновляется при Close, не при Open)
