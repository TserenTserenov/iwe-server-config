# Протокол Open (ОРЗ-фрактал)

> **Три масштаба:** День, Неделя и Сессия. Триггер определяет масштаб.
> **Источник:** CLAUDE.md § 2 (slim) → этот файл. **CGUS (WP-481 Ф5):** порядок шагов ниже = порядок удержания внимания, НЕ порядок исполнения. `[[gate]]`/`[[gate:AR.NNN]]` = предусловие «без этого работы нет» (блокирует); `[[narrative]]` = демонстрационный порядок (skippable). Вход «с середины» штатен, если все gate соблюдены.

## § Масштаб: День → skill `/day-open`

> **Триггер:** «открывай» / «открывай день». Полный алгоритм → `.claude/skills/day-open/SKILL.md`. **Исполнение:** пошагово через `task_tracker.create` (Host Contract DP.IWE.011 §5), каждый шаг = задача, блокирующее. Close пока вне объёма этой миграции — см. `DP.IWE.011` §9.

> **Вчерашний WakaTime (pending-мультипликатор):** в шаге 1 «Вчера» — проверить наличие `day_close` записи за вчера в Neon (`domain_event WHERE event_type='day_close' AND external_id='day-close-{вчера}'`). Если отсутствует: запросить WakaTime API `summaries?start={вчера}&end={вчера}` → пересчитать мультипликатор → дозаписать в domain_event. Причина: `--today` CLI не даёт данных за прошлый день (WP-299 Ф4 п.3).

## § Масштаб: Неделя → документы `current/WeekPlan`/`WeekState`/`WeekReport`

> **Триггер:** сессия, единственный результат которой — сам документ недели: правка направлений/РП в Плане недели в любой день недели (актуализация), стратегирование в понедельник (`skill strategy-session`), закрытие недели (`skill week-close` / `/run-protocol week-close`). **WP Gate не применяется** — предмет работы не чей-то рабочий продукт, а сам живой документ недели, по той же логике, что и масштаб «День» выше. Добавлено 17.09.2026 по решению пилота (пир-сессия с Kimi, актуализация WeekPlan W38) — до этой правки масштаб «Неделя» не был явно выведен из-под WP Gate, чем и объясняется прежняя практика подвешивать такие сессии на РП-561.
> Правка МЕХАНИКИ конвейера (шаблон, автосборка, скрипты открытия/закрытия дня/недели) — другой масштаб, не этот: туда РП-561 «Конвейер закрытие-открытие сессии-дня-недели-месяца».

## § Масштаб: Сессия (Session Open)

### Шаг 0. Маршрутизатор (DP.ROLE.059) — перед WP Gate · [[narrative]]


#### Совпадает — работаем

1. Ссылаемся на номер РП.
1b. **Background Gate (Ф18):** в дневном ledger (`machine/ledger/day-<today>.yaml`, kind: `session_closed`) найти последнюю запись этого РП (поле `wp`) — `data.status == in_progress_background` без более поздней записи `kind: deferred_work_done` того же РП → сообщить пилоту «фоновый хвост предыдущей сессии не завершён», предложить выбор: подождать / перехватить. Нет такой записи или `status` другой (включая `unknown` — до передачи `status` пилот-протоколом закрытия, `protocol-close.md` п.2) → пропустить, продолжать как обычно. **Известные пробелы (гейт пока не может сработать положительно ни разу):** (1) `deferred_work_done` — эмиттер при реальном завершении фона не реализован (CONCEPT-night-cycle.md §19 п.3, часть Ф16.7, не Ф18); (2) поле `status` в `session_closed` попадёт со значением `unknown`, пока закрывающая сессия не передаёт его явно — раннер не резолвит поля между шагами автоматически.
2. **DayPlan Gate:** РП нет в DayPlan → добавить строку. strategy_day → пропустить. [[gate]]
3. **Sync Gate (актуализация контекста РП).** Прочитать контекст РП и связанных РП → синхронизировать открытые фазы с тем, что фактически сделано. **Цель:** исключить дублирование работы, ложные блокеры, неверные оценки в Ритуале. [[gate]]

   **Race-guard:** если state-файл `.claude/state/wp-sync-<N>.done` существует И его mtime моложе 8 часов — пропустить (sync уже выполнен в этой сессии). Если файл есть, но mtime старше 8h — считать stale: `rm -f` и продолжить заново. Проверка: `find .claude/state/wp-sync-<N>.done -mmin -480 2>/dev/null` (пустой вывод = нет файла или stale → запускать; непустой = свежий → пропускать).

   **Шаг 3a — Bundle.** Запустить детерминированный сборщик контекста, захватывая exit-код в ТОМ ЖЕ вызове Bash (не `2>&1` — bundle пишет `[WARN]` в stderr до первой строки stdout, слияние потоков ломает контракт «первая строка = машинный статус»):
   ```bash
   bash "${IWE_WORKSPACE:-$HOME/IWE}/.claude/scripts/wp-sync-bundle.sh" WP-N > /tmp/wp-sync-bundle-$$.md; BUNDLE_RC=$?; head -2 /tmp/wp-sync-bundle-$$.md; echo "bundle_rc=$BUNDLE_RC"
   ```
   Экономичный slug `$$` — только в пределах ОДНОГО вызова Bash-инструмента (переменная не переживает границу между вызовами) — работать с файлом и удалять его в этом же вызове или через путь, зафиксированный в этой же команде.

   | Exit | Значение | Действие |
   |------|----------|----------|
   | 0 | РП найден, `GIT_SYNC_STATUS: OK` или `NO_UPSTREAM` | читать вывод как обычно |
   | 1 | РП не найден | перейти к Ритуалу с пометкой «контекст не найден» |
   | 2 | ошибка парсинга frontmatter | перейти к Ритуалу, поднять stderr в «Требует внимания» |
   | 3 | `GIT_SYNC_STATUS: STALE\|DIVERGED\|fetch_failed\|checker_unavailable` (WP-561 Ф20) — рабочая копия governance-репо не синхронизирована с origin или сверка не подтверждена | см. ниже, НЕ переходить к 3b/3c молча |

   **Exit 3 — рецепт по среде:** изолированная сессия (свой worktree, `session-guard.sh open --isolate`) → повторить Шаг 3a с `IWE_WORKSPACE` на этот worktree, он обычно свежий от `origin/main`. Канонический чекаут → не форсировать pull (AR.006, Pull-on-Touch); либо `session-guard.sh open --isolate` и повтор оттуда, либо, если пилот явно согласился работать по неполным данным, добавить `--force-sync` к вызову bundle и process дальше — статус `GIT_SYNC_STATUS`/`GIT_SYNC_OVERRIDE` из первых двух строк вывода обязательно процитировать пилоту одной строкой ДО решения, не молчать о нём.

   **Шаг 3b — Override (опционально).** `bash .claude/scripts/load-extensions.sh protocol-open sync` — exit 0 → `Read` файлы (alphabetic), они переопределяют дефолтное поведение шага 3c. Exit 1 → дефолт.

   **Шаг 3c — Дефолтное поведение по веткам (только при `BUNDLE_RC` = 0; при 3 — см. выше, не входить сюда без `--force-sync` или явного решения пилота):**
   - **Ветка A — тривиальный случай** (≤1 связанных РП И drift-сигналов нет): главный агент сам читает контекст текущего РП и патчит маркеры (`[ ]` → `[x]` для подзадач, ссылающихся на закрытые связанные РП).
   - **Ветка B — нетривиальный** (≥2 связанных РП ИЛИ есть drift-сигналы): делегировать через Task tool sub-agent'у `wp-sync-actualizer` (Sonnet 4.6, context isolation). Передать в prompt: номер WP-N + содержимое bundle (включая секцию «Git-sync рабочей копии» — sub-agent проверяет её сам, повторного fetch не делает). Sub-agent возвращает unified diff в формате `---ORIGINAL---`/`---REPLACEMENT---`. Главный агент применяет через Edit.
   - **Ветка C — противоречие** (sub-agent вернул раздел «Требует внимания» вместо diff'а, или нашёл «PASS» в одном связанном vs «FAIL» в другом по той же метрике): НЕ применять автоматически, поднять в «Требует внимания» Ритуала.

   **Шаг 3d — Очистка:** `rm -f /tmp/wp-sync-bundle-$$.md`. Маркер `touch .claude/state/wp-sync-<N>.done` — **только если `BUNDLE_RC` = 0 И `GIT_SYNC_STATUS: OK`** (не после `--force-sync`, не после `NO_UPSTREAM` — race-guard не должен 8 часов молчать по данным, которые сам bundle не подтвердил как синхронные).

3.5. **Обязательная актуализация при переоткрытии (WP-530 Ф66, пир-сессия Claude+Kimi+Codex 2026-09-25-16-wp530-instant-sync-mandatory-reopen, ArchGate пройден условно 25.09.2026; заменяет прежний «мини-ритуал переоткрытия» целиком, не живёт рядом с ним — два параллельных вердикта давали противоречие).** Состояния: `reopened → actualization_required → actualized → editing_allowed`. Механизм — `~/IWE/scripts/wp-reopen-gate.sh` (детерминированный скрипт, не LLM-решение; A.21 GateProfilization FPF — гейт публикует решение как воспроизводимый факт, не как нарративное «пилот сказал да» в чате):
    ```bash
    bash "${IWE_SCRIPTS:-$HOME/IWE/scripts}/wp-reopen-gate.sh" check-edit --wp N --governance-repo "$GOV_REPO_ROOT"
    ```
    **Exit 0** (`editing_allowed`) → продолжать. **Exit 2** (сообщение самообъясняет причину: нет лицензии / лицензия чужой сессии / лицензия истекла по TTL / карточка изменилась на origin с момента актуализации) → выполнить актуализацию и повторить:
    ```bash
    bash "${IWE_SCRIPTS:-$HOME/IWE/scripts}/wp-reopen-gate.sh" actualize --wp N --governance-repo "$GOV_REPO_ROOT" --session-id "$SESSION_ID"
    ```
    `actualize` делает `git fetch` и записывает лицензию, привязанную к цифровому отпечатку (digest) карточки НА ORIGIN на момент вызова + защитный токен (fencing token) + TTL 8ч — не булев флаг. Отсюда следствия: (а) карточка на origin изменилась после актуализации → лицензия сама инвалидируется при следующей проверке, не только по TTL; (б) коммит ДРУГОГО, не связанного РП НЕ инвалидирует эту лицензию — привязка идёт по цифровому отпечатку конкретно этой карточки, не по всему репозиторию; (в) лицензия другой сессии на тот же РП не даёт прав текущей. **Проверка обязательна перед первой содержательной правкой карточки этого РП в сессии** (не перед самим открытием сессии, не перед чтением/диагностикой/эскалацией — те не блокируются).

    **Аварийный люк при недоступном origin (`closure_pending_sync`).** Обычная актуализация невозможна днями (реальный сетевой отказ) → пилот (не агент сам себе) вызывает двухшаговый вызов с кодом-вызовом:
    ```bash
    bash "${IWE_SCRIPTS:-$HOME/IWE/scripts}/wp-reopen-gate.sh" closure-pending-sync request --wp N --reason "<причина>"
    # показать код пилоту, получить его обратно
    bash "${IWE_SCRIPTS:-$HOME/IWE/scripts}/wp-reopen-gate.sh" closure-pending-sync confirm --wp N --challenge-response <код от пилота>
    ```
    Это не криптографическое доказательство «это точно пилот» (сильнее нет ни у одной точки согласования в этой платформе — тот же уровень доверия, что у WP Gate «дождаться согласования пилота»), но живой раунд-трип через код, который видит человек, не только слово «роль». После confirm — неизменяемая аудит-запись (`~/IWE/.iwe-runtime/wp-reopen-leases/closure-pending-sync-audit.jsonl`), обычные правки карточки остаются заблокированы до разрешения конфликта пилотом при восстановлении связи.

    **Известная граница (честно, не замалчивать).** Сам текст этого протокола (`memory/protocol-open.md`) — личная память Мака без общего git-remote, доставки на Цех не имеет; описанный здесь ритуал действует только на агентов, которые читают именно этот файл на этом хосте. Механическое ограждение (сам скрипт `wp-reopen-gate.sh`) доставляется на оба хоста штатным конвейером `iwe-local-config`/`scripts` (тот же канал, что доставляет `session-guard.sh`) — оно и есть настоящая защита, независимая от того, кто и какую память читает.

    **Совместимость со старым race-guard Sync Gate (Шаг 3, выше).** `wp-sync-<N>.done` (8ч TTL) и `--force-sync` НЕ подтверждают актуализацию по смыслу этого шага — это отдельный, более узкий механизм (проверяет свежесть git-синка рабочей копии, не привязку к конкретной ревизии карточки конкретного РП). Пройти Sync Gate ≠ пройти этот гейт; оба выполняются, ни один не отменяет другой. [[gate]]

**Режим ТВС (конвейерная модель):** текущее = штатная операционная работа (держит норму); важное = поднимает норму выше прежней (развитие, R{N}); срочное = угроза остановки конвейера (прод/биллинг упал, блокер). «Срочное» НЕ присваивается по дедлайну или по силе «горит» ([[Дедлайн ≠ Срочность]]) — только по физической угрозе остановки. Настоящее срочное обычно не идёт через Ритуал (прерывает и чинится), но фиксируется постфактум.
