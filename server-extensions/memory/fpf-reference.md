# FPF (First Principles Framework) — справочник

> Источник: `{{HOME_DIR}}/IWE/FPF/FPF-Spec.md` (4.6 MB, ~50000 строк)

## Когда читать FPF

- При работе с концепциями Level 1 (мета-онтология)
- При неясности базовых различений (Role/Method/Work, System/Episteme)
- При необходимости точной формулировки паттерна (A.*, B.*, etc.)
- При создании/проверке Pack на соответствие FPF

## Как читать

- НЕ читать целиком
- Сначала оглавление (первые 200 строк), потом нужную секцию
- Grep для конкретных паттернов (например, `A.7` для Strict Distinction)

## Структура FPF

- **Part A** — Kernel: Holon, BoundedContext, Role-Method-Work, Signature Stack
- **Part B** — Aggregation (Γ), Trust (F-G-R), Evolution Loop
- **Part C** — Domain extensions: Sys-CAL, KD-CAL, Kind-CAL, NQD-CAL, CausalUse-CAL
- **Part D** — Ethics & Conflict
- **Part E** — Constitution & Authoring
- **Part F** — Terminology unification (UTS, Bridges)
- **Part G** — SoTA Kit

## Критерий отбора паттернов (WP-525 Ф1, консенсус пир-сессии с Codex 19.08)

- **ADD** — паттерн попадает в индекс/получает карточку, если реально повлиял на записанное решение (АрхГейт, обоснование, секция «в нашем коде») — не по факту, что «показался важным». Полнотекстовый поиск по `FPF-Spec.md` — усиливающий сигнал, не обязательный.
- **REMOVE-кандидат** — нет влияющих применений за 90 дней И нет `related`-связи с активным паттерном — решает куратор на очередной сверке, не автоматика.
- **Staleness-guard** — при каждой синхронизации с апстримом грепать код каждого паттерна из индекса в текущем `FPF-Spec.md`; не найден → пометка `[BROKEN: ...]`, решение пилота, не тихое удаление (прецедент — A.6.8 ниже).
- **Лимит объёма** — мягкий SLO (сейчас индекс держим до ~60 строк), не встроенный триггер REMOVE.

| Данные ≠ Представление | Внутреннее vs внешнее |

## Терминология ailev ↔ IWE (DPF/SPF/TPF/LPF, WP-448 Ф8)

> Анатолий Левенчук (ailev) переименовал Second Principles Framework в DPF (Domain Principles Framework), стек `FPF → DPF → LPF` (ядро → предметный свод → свод местной практики; ZPF, SPF, TPF в FPF — входные псевдонимы). В IWE переименование не планируется — только сноски (CLAUDE.md §1, SPF/README.md). Таблица ниже — словарь перевода при чтении его текстов.

| ailev-термин | IWE-эквивалент | Примечание |
|---|---|---|
| DPF (Domain Principles Framework) | Pack (SPF-инстанс) | формальная эквивалентность, не переименование |
| TPF (Third Principles Framework) | DS + операционный слой агента | процессный TPF vs контентный TPF — см. [[TPF ≠ DS]] |
| LPF (local practice framework, свод местной практики; `FPF-Spec.md` L.69994) | практика нашей IWE (CLAUDE.md, протоколы, гейты, хуки, скиллы — прежде «TPF-процессный»), практики МИМ или компании | исправлено 29.10 по FPF Library.Reference:10, E.4.DPF; прежнее «практики роли конкретного носителя» ошибочно — это личная практика носителя роли (DP.D.178), частный случай местной практики. По форме LPF — полноценный пакет наравне с DPF (свой манифест/издание, `E.11.PFP`); детали → `memory/repo-type-rules.md` |
| `E.4.DPF` (authoring-каркас) | `SPF/pack-template/` + `SPF/process/01-11` | оба задают форму и процесс наполнения домена |
| NSTD (слоты метод-карточки: Forces, Bias-Annotation, ...) | `_method-card-template.md` (обогащение — WP-448 Ф9) | наш формат карточки метода обогащается двумя разделами по образцу NSTD |
| Нарративизация (narrativization) | Фабрика руководств (WP-364) | метод превращения структуры в учебный текст — берём по ссылке, без дублирования содержания |
